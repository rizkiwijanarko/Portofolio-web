## Overview

**Orla.co** is a boutique digital fashion platform for modern Indonesian women seeking modest, versatile, and elegant everyday apparel. It combines an editorial storefront with practical local commerce workflows, including BCA bank transfer and QRIS payments, map-based delivery pin location selection, and multi-courier shipping via Biteship.

Built with **Next.js 15 (App Router)**, **TypeScript**, **Prisma ORM**, and **PostgreSQL**, the platform bridges high-fashion editorial aesthetics with robust transactional integrity.

## The Problem

The client needed more than a basic product catalog. They required a custom digital storefront reflecting luxury brand craftsmanship while addressing the operational realities of Indonesian e-commerce:

- **Inventory overselling**: Manual payment confirmation (BCA transfer / QRIS) takes time. Traditional platforms allow stock to be claimed by multiple buyers while payment verification is pending.
- **Dynamic Indonesian logistics**: Couriers vary by price, coverage, and speed. Customers need pinpoint map selection and real-time rate comparison (JNE, SiCepat, J&T, instant couriers).
- **Client & server leakage**: E-commerce apps often bundle server-only logic, payment secrets, and image manipulation libraries into client bundles, causing bloat and security hazards.

## The Solution: Core Experience

Orla solves these operational challenges through an **order-first checkout** pipeline, an isolated admin workspace, and a seamless customer experience.

## Key Engineering Decisions & Trade-Offs

- **Order-First Atomic Stock Reservation**:
  - *Context*: In manual transfer and QRIS flows, payment is not instantaneous.
  - *Decision*: Orders atomically decrement available stock on creation and set a 2-hour payment window. If payment proof is not uploaded, an automated cron restores inventory.
- **Decoupled Order Creation from Payment Verification**:
  - *Context*: Requiring instant payment confirmation before order creation creates race conditions.
  - *Decision*: Separated the checkout transaction from receipt upload and admin review, ensuring inventory state remains unambiguous.
- **Single Logistics Aggregator (Biteship)**:
  - *Context*: Managing separate APIs for JNE, SiCepat, J&T, and Grab is fragile and high maintenance.
  - *Decision*: Integrated Biteship as a unified gateway for rate calculation, automated AWB generation, and webhook-driven tracking.
- **Strict Seam Pattern for Zero Bundle Leaks**:
  - *Context*: Accidental imports of Node utilities (`sharp`, `crypto`, `fs`) in React components cause hydration failures and security vulnerabilities.
  - *Decision*: Enforced strict directory boundaries where UI components only communicate with backend domains through typed server actions and route handlers.

## Hard Engineering Challenges

### Concurrent Checkout Race Conditions
- **The Challenge**: Multiple customers attempting to purchase the last available unit of a popular dress simultaneously.
- **Solution**: Implemented PostgreSQL serializable transactions via Prisma to perform atomic conditional decrements (`WHERE stock >= requested_quantity`), immediately failing competing requests with friendly out-of-stock messages.

### Geocoded Delivery Pin Mapping & Rate Calculations
- **The Challenge**: Indonesian street addresses often lack precise postal matching, resulting in incorrect delivery fees.
- **Solution**: Built an interactive Leaflet coordinate picker that geocodes the customer's exact pin location and feeds high-precision latitude/longitude directly into Biteship's routing engine.
